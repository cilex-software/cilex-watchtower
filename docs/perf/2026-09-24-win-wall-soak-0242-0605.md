# 16-camera wall playback soak, 02:42–06:05 — re-open is consistent, in-stream seek never works

Booth `wt-sm-vnutri-01` (i5-12400, Win 11), app `1.1.599 c87b1b44-dirty`, run as a second
instance beside the guard's live wall. **26 runs, 593 measured navigation steps, 3 h 23 m.**

Cameras: the sixteen continuously-recorded street cameras
`102 105 110 113 115 116 117 118 119 122 123 125 126 127 129 130` — the operator's own
wall set. Hall/lift/roof cameras were excluded deliberately: they record on motion, so
their archive has holes by design and a jump into a hole scores as a latency failure
that is really an empty archive.

## Result

    reopen   193 / 193  OK        (100%)
    seek     400 / 400  TIMEOUT   (0% — not one succeeded, all night)

**Re-open latency**, the path that actually navigates:

## Is it consistent? Yes — and that was the question

    02:00   n= 16   p50  7,434 ms   min 4,903   max 13,068
    03:00   n= 56   p50  7,981 ms   min 4,934   max 15,016
    04:00   n= 61   p50  8,635 ms   min 4,898   max 14,169
    05:00   n= 56   p50  8,335 ms   min 4,917   max 15,636
    06:00   n=  4   p50  7,366 ms   min 7,020   max 11,598

p50 stays inside **7.4–8.6 s** across three and a half hours — a 16% spread with no drift
and no degradation. The floor is flat at ~4.9 s in every single hour, which is the more
telling number: the best case does not rot. The ceiling wanders between 13 and 15.6 s.

By jump distance, re-open is close to distance-independent, as it should be — a re-open
is a fresh session, so the work is compositor warm-up, not travel:

    1 day back  (1440 min)   n=100   p50 7,466 ms
    2 days back (2880 min)   n= 93   p50 8,534 ms

**Memory**: each run is a fresh process (max uptime 480 s), so no cross-run leak is even
possible; within that, median RSS by hour was 641 / 647 / 667 / 677 / 672 MB — flat, and
it plateaus rather than climbing.

**The guard's wall was untouched**: 35 live pipelines throughout and **zero** SLOW,
error, `pipeline_error` or `decode_fail` lines in its flight recorder across the whole
02:00–06:00 window.

## The seek result is not flakiness, it is a constant

400 attempts, 400 timeouts, four jump distances (10/30/60/120 min), both directions, 26
independent process lifetimes, across four hours. A wall that reviews recorded footage
cannot navigate in-stream at all. Root cause and evidence:
`docs/perf/2026-09-24-win-wall-seek-does-not-seek.md` — cilex-vision emits one
`#EXT-X-DISCONTINUITY` per segment (3,593 of 3,594), so FFmpeg sees that many independent
timelines and will not seek across them. Letter filed.

The practical consequence, now quantified: **every navigation on this wall costs a full
session re-open at a p50 of 8.2 s**, because the cheap path does not function.

## Two harness defects the soak exposed in itself

**The runner tallied every run as `steps=0 ok=0 timeout=0`.** It counted WALLPERF lines
from the child's *stdout*; Qt routes `console.log` to the flight recorder and ffmpeg's
own chatter to stderr, so stdout was empty all night. Nothing was lost — the flight
recorder had all 593 — but the live progress line was useless for three hours. I had
already established where those lines go earlier the same night and then wrote the runner
as if I had not.

**My own monitor corrupted the summary log.** A `tail -F` held
`soak-logs/soak-summary.log` open, and every `Add-Content` in the runner failed with a
sharing violation, so the summary stops after four lines. The run record survived only
because the runner also writes to stdout. Watching a file is not free on Windows: use a
read-only share mode, or watch a copy.
