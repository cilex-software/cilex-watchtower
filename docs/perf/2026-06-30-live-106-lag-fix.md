# P0 #2 fixed — .106 Live-wall "2–3 s lag": armed-priority live slots + faster snapshot + SNAPSHOT badge

## Cause (recap)
.106 lagged ~2–3 s while .201 was real-time because the wall live-decodes only `maxLiveDecodes` (9) tiles and
allocated those slots **by IP-sort position** — .106 sat past the cap, so it showed a `LiveThumb` snapshot
polled every **4 s**, not a live decode. .106 is **motion-armed**, yet was deprioritised behind idle cameras
purely by position.

## Fix (3 parts; `maxLiveDecodes` UNCHANGED — no memory regression / P0 #1 budget intact)
1. **Faster snapshot refresh** — `LiveThumb.refreshMs` 4000 → **1000** (env `WT_THUMB_REFRESH_MS`). Capped
   tiles are now ≤1 s stale, not 4 s. Cheap now that snapshots ride the cached query-api endpoint.
2. **Importance-ranked live slots** — `LiveMonitor.liveDecodeSet` ranks the page's cameras **armed-first**
   (then position) and takes the top `maxLiveDecodes`; `liveDecodeAllowed` keys off that set. So **armed
   cameras get the live decodes ahead of idle ones**. With nothing armed it's the old position order.
3. **SNAPSHOT badge** — decode-capped tiles show a `◌ SNAPSHOT` pill so a periodic still isn't mistaken for a
   live (or frozen) feed.

## Verified on-device (build68)
- **3 cameras armed** (.106, .120, .201) ≤ cap 9 → all armed get live slots ⇒ **.106 is now LIVE / real-time**,
  not a snapshot. (Before: .106 at sort position ~10 → snapshot.)
- **go2rtc `:1984` snapshot wakes = 0** — snapshots use the cached `:8000` endpoint; query-api absorbed the
  1 s poll (~130 reqs/30 s), **go2rtc stable (RestartCount 0)**, mem ~46 MB.
- **Live decodes still 9** (`:8554` RTSP) — `maxLiveDecodes` unchanged.
- Screenshot (`WT_SCREENSHOT`): capped tiles show `◌ SNAPSHOT`; live tiles don't.
- Both Qt builds clean.

## Notes / trade-offs
- `liveDecodeSet` recomputes on **roster/sort/page** changes, not every status poll — **stable** (avoids
  live-slot thrash; each slot change is a pipeline build+teardown). A camera that arms mid-session gets a live
  slot on the next page/sort interaction. (A status-triggered recompute with hysteresis could be added later
  if operators need instant promotion on arm.)
- Promoting armed cameras means an idle camera previously at position 7–9 may drop to a (now ≤1 s) snapshot —
  the intended trade (watch what's armed, not what's idle).
- The RSS-shed safety valve (P0 #1) still collapses `maxLiveDecodes`→1 under memory pressure.
