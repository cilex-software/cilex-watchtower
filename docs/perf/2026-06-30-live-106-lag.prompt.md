# P0 #2 — Live wall: ".106 lags 2–3 s" (decode-capped tile shows a slow snapshot, not live)

## Context (established)
On the Live wall the operator saw camera **.106 lag ~2–3 s behind reality** while **.201 was real-time**
(compared hand-raise timing). Root cause, confirmed during the go2rtc investigation:
- The wall live-decodes at most `maxLiveDecodes` tiles (default **9**); tiles **beyond** the cap show a
  **periodic snapshot** (`LiveThumb`), not a live pipeline.
- Live-decode slots are allocated **by grid/sort position** (`LiveMonitor`: "the first `maxLiveDecodes` tiles
  run a live VA-API pipeline"). **.106 sits past the cap → snapshot mode; .201 is within it → live.**
- `LiveThumb.refreshMs = 4000` → a capped tile's image is up to **4 s stale** → reads as a 2–3 s lag. A truly
  live tile (rtspsrc sub, ~150 ms jitter) is sub-second.

So it's working-as-designed, but two things make it feel broken: the snapshot refresh is slow, and an
**important camera (.106 is motion-ARMED) is treated as less important than idle cameras** just because of its
IP-sort position — while the tile badge gives no hint it's a periodic still, not live.

## What changed since (this unblocks the fix)
The go2rtc snapshot path is now a **cached + single-flight + concurrency-bounded query-api endpoint** with a
recorded-keyframe fallback (this session's go2rtc thread). Snapshots are now **cheap** (per-camera ~10 s TTL,
served ~0.001 s warm / ~0.17 s cold, **no go2rtc producer wake**). So polling capped tiles **faster** no longer
stresses go2rtc — the old reason `refreshMs` was 4 s.

## Goal
On the wall: (a) decode-capped/snapshot tiles refresh within **~1 s** (not 4 s); (b) **important cameras
(armed / recent-motion / selected) are prioritised for the live-decode slots** so they're real-time, not
capped behind idle cameras; (c) the operator can tell **live vs snapshot at a glance**. All **without** raising
the memory/OOM budget (P0 #1) or re-stressing go2rtc.

## Plan
1. **Quick win — faster snapshot refresh.** Lower `LiveThumb.refreshMs` (e.g. 4000 → ~1000, ideally env-tunable
   `WT_THUMB_REFRESH_MS`). Then **verify the cached endpoint absorbs it**: query-api snapshot request rate is
   fine, the per-camera 10 s TTL still coalesces (a 1 s poll mostly hits cache), and **go2rtc snapshot wakes
   stay 0** (check `:1984`), no go2rtc RestartCount change. The double-buffered `LiveThumb` already avoids
   blanking on refresh.
2. **Prioritise live-decode slots by importance, not position.** In `LiveMonitor`, choose which tiles get the
   ≤`maxLiveDecodes` live pipelines by a priority key — **armed > recent-motion/recent-event > operator-
   selected > position** — instead of pure grid order. Net: an armed camera like .106 gets a live slot; an
   idle one drops to snapshot. Keep it stable (hysteresis / don't thrash slots as priorities flicker — each
   slot change is a pipeline build+teardown).
3. **Make snapshot-mode legible.** Give capped/snapshot tiles a clear, subtle indicator (e.g. an "SD"/period
   marker or a distinct badge) so a ~1 s-refresh still isn't mistaken for a frozen live feed. (The "LIVE"
   badge today doesn't distinguish live-decode from snapshot.)
4. **Decide + document the trade-off.** Faster refresh gets capped tiles to ~1 s; only a live slot gets
   real-time. Recommend: prioritise the important cameras for live (real-time where it matters) **and** speed
   up the rest's refresh (acceptable for idle tiles). Don't just raise the cap (that's the P0 #1 memory/OOM
   tension; the RSS-shed valve is the backstop, not a licence to raise it).

## ⚠ Constraints
- **Memory:** keep `maxLiveDecodes` bounded — do NOT raise it to "fix" the lag. The live-pipeline leak under
  go2rtc instability (P0 #1) is contained by the RSS-shed valve, not solved; more live decodes = more risk.
- **go2rtc:** the faster poll must ride the **cached** endpoint (the client renders the backend `snapshot_url`,
  now the query-api cached URL). Verify go2rtc wakes stay 0 and it doesn't OOM. Don't point snapshots back at
  `frame.jpeg`.
- **Box is OOM-sensitive / shared** — bounded, watched test runs (see the P0 #1 prompt's safety notes).
