## §3 THE COVERAGE CAVEAT — read this before trusting §1

`livePipes` (number of live decode pipelines) across the 963 samples:

|---|---|---|

The random walk parked the app **off the Live wall for most of the run**. So this
soak validated **UI / navigation / triage / playback endurance**. It did **NOT**
validate sustained 16-stream decode endurance on the UHD 730 — the wall was at
full tilt for about 10 minutes of the 8 hours. The clean crash record in §1 must
not be read as "the wall survives 8 h", and the §2 memory curve is dominated by
event/triage/playback work, not by the wall.

A wall-pinned soak is a separate run and is not covered here.

## §4 Defects found

**D1 — `events/<id>/snapshot` returns HTTP 404 at very high volume.**
`qml/EvSnapshot.qml:82` requests the stored event still via the `cvframe`
provider. **17 218 × `QML QQuickImage: HTTP 404`** in 8 h (~36/min); it is 91 %
of all log output for the window. The client handles it correctly — the design
at `EvSnapshot.qml:70-90` gates a go2rtc live-frame fallback on the still having
actually failed, and falls through to an honest "no frame" state — so the UI is
not lying. But the volume says most events in this site's queue have **no stored
still on the backend**, and every one of them costs a round trip plus a fallback
attempt. This is a question for CV, not a client fix.

**D2 — `qml/EventsArea.qml:359` TypeError ×171.**
`TypeError: Value is undefined and could not be converted to an object`. Fired
while the driver was walking the triage queue and switching tabs/filters. Real
client bug; needs the undefined guard at that line.

**D3 — `qml/LiveMonitor.qml:1736` TypeError ×60** (48 + 12 at a second column).
Same class, on the live wall path.

**D4 — `QIODevice::read (QNetworkReplyHttpImpl): device not open` ×190.**
A network reply is being read after it closed. Harmless-looking, but it is a
use-after-close on the reply object and worth tracing.

**D5 — `create group failed 409` (15:17:49).**
A random click hit group creation with a name that already existed. The 409 is
the backend behaving correctly; what is NOT established is whether the UI
surfaced it honestly to the operator or swallowed it. Needs a deliberate repeat.

**D6 — top-bar clock shows a stale time for up to 10 s after the window is
re-exposed.** Found pre-flight: at system time 09:53:22 the clock read `19:15`
— 14 h 21 m stale — and corrected within the next minute. Cause is
`qml/TopBar.qml:30`: `root.now` is refreshed only by a 10 s QML `Timer`, and QML
timers are animation-driven, so they do not advance while the window is not
exposed; the capture was 700 ms after the window was foregrounded. So the
severity is **a ≤10 s wake-up transient, not a permanently frozen clock**. In a
booth where guards read the wall clock it is still worth fixing — refresh `now`
on visibility change as well as on tick.

**D7 — 39 log lines are unreadable (`U+FFFD` replacement chars).**
`qml/LiveMonitor.qml:1736` image errors log as `EF BF BD` repeated (verified at
byte level). The flight recorder is **not** at fault — it converts with
`msg.toUtf8()` at `src/models/FlightRecorder.cpp:130`; the replacement chars are
already in the QString. The loss is upstream, most likely a localized (Russian)
Windows error string decoded with the wrong codepage before Qt hands it over.
Low severity by count, but those 39 lines are exactly the "why did this image
fail" explanation, so they are the ones you want readable. Cause not established.

## §7 Two faults in the harness, both mine

1. **Per-click log lost after 10:02:24.** The crash-watch monitor was armed on
   `tail -F soak-monkey.log`; on Windows that holds a lock, and every subsequent
   `Add-Content` in the driver failed with `IOException`. `$ErrorActionPreference
   = "Continue"` meant the driver **kept clicking for the full 8 h** — proven by
   84 tour screenshots through 18:02 and by the continuous metric series — but
   the record of *which* random coordinates were hit is gone, and 5.3 MB of
   identical IOException text went to the task output instead. Do not tail the
   log a Windows writer is appending to; write the action log through a handle
   opened `FileShare.ReadWrite`, or have the driver own the tail itself.
2. **CSV corrupted by locale for the first ~2 rows.** `[math]::Round(328.4,1)`
   renders as `328,4` under ru-RU and split the CSV into 23 columns. Caught in
   the first minute, fixed with invariant formatting
   (`soak-monitor.ps1`, `function N`), monitor restarted at 10:01.

Neither fault touched the application under test.
