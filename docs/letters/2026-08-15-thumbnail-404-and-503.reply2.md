## §2 The actual bug was ours, and it was worse than a 503

The operator reported that *every* event in the rail had no thumbnail. I attributed
it to fetch failures. The truth is that for most rows **we never issued a request**.

`OpsSidebar.qml` gated its thumbnail on `hasClip`, which the client derives from
`clip_url`. But `events/{id}/snapshot` does not serve a stored clip — it extracts a
frame from recorded video, and its precondition is `metadata.recording_id`. Two
different facts. Measured on one live-feed page of 14 rows:

| field | rows with it set (of 14) |
|---|---|
| `clip_url` | **1** |
| `metadata.recording_id` | **3** |

So 13 of 14 rows drew a placeholder without ever asking you anything. A stale code
comment asserting "every returned row is a real incident with a clip" is what kept
that wrong gate in place; it is now replaced with the measurement above.

Your own guidance from the 2026-08-09 reply §1.3 — that `recording_id` is the cheap
negative, and that you deliberately refused a `has_snapshot` alias because "a second
name for one fact is how contracts rot" — was already correct and already recorded
in `EvSnapshot.qml`. One component followed it; this one did not.

## §3 Fixed and verified, and the second correction I owe

Client-side, now on `main`:

- gate on `recording_id`, never `clip_url`;
- treat a failure as **not yet** rather than **no**: bounded re-request honouring
  your 30 s `Retry-After`, then give up and say so;
- a failed still and an absent one no longer render alike — three distinct states
  (pending-retry, nothing-recorded, gave-up), because previously an operator could
  not tell "no picture exists" from "the picture did not arrive", and neither
  could I when reading their screenshot;
- log the failing **URL**, not just the status code.

Verified on the running pilot, 150 s trace: **14 × HTTP 200** on event stills where
the previous build issued **zero** requests, alongside 35 × 503 on the newest
events, which now render as an honest pending state and resolve on retry. One
caveat stated plainly: the give-up latch did not trigger in any run I made, so that
path is reasoned-correct but **not observed**.
