## 4. Four things your Windows leg does to the monitoring contract

This is the section I would not want you to meet on rollout day. None of it changes the
contract; all of it changes what the contract *means* on Windows.

**(a) `machine_id_hash` has no `/etc/machine-id` equivalent, and my station identity is
built on it.** I key a station on `machine_key` = `machine_id_hash`, falling back to
`host:<hostname>`. Two failure modes, both silent:

- If the Windows source is **unstable** (regenerated by an OS repair, a sysprep, a domain
  rejoin), the box arrives as a *new station*: new row, new 5 GB quota, its crash history
  orphaned from the old identity, and — worse — its `no_heartbeat_support` grace resets, so
  it is briefly unmonitored again.
- If it is **not unique** (a cloned VM image or a golden disk deployed without
  regeneration), several boxes collapse into **one** station. They would share a quota, and
  a heartbeat from any one of them would make all of them look supervised. That is the
  dangerous one, because it manufactures exactly the false confidence this monitoring
  exists to remove.

`HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` is the usual answer and is stable across
reboots but **is captured by disk imaging**, so if guard boxes are deployed from an image it
must be regenerated or salted at install. My ask: whatever you pick, hash it the same way
(`sha256:…`) and treat "is this stable and unique across our actual deployment method?" as a
test rather than an assumption. If you tell me the source, I will note it in the spec so a
future me does not have to infer it from data.

**(b) My alarm window is calibrated to systemd, and Windows has none.** The 10-minute
`for:` on the critical alert is justified by *systemd restarting Warden in ~2 seconds* — so
ten minutes of silence means the supervisor of the supervisor failed. Task Scheduler
at-logon is a different animal: it starts Warden at logon and, depending on how you
configure it, may not restart it at all if it dies mid-session. If that is the case, then on
Windows **a dead Warden stays dead until the next logon**, and ten minutes is no longer a
"this is definitely broken" threshold — it is simply the point at which I notice. That is
fine, but tell me, because if Windows has no auto-restart I would rather the alert text said
so: the remedy on Linux is "check the unit", on Windows it is "someone must log the box back
in or re-arm the task". Same alert, different human action.

**(c) A batch install will hit my self-registration ceiling.** I cap
**20 new self-registering stations per hour** (a defence against a leaked bootstrap secret
minting identities). A staged rollout is unaffected. But if you image and power on **more
than 20 Windows boxes in the same hour**, the ones past 20 get `429` on their first upload
and retry with backoff — they will land eventually and nothing is lost, but the rollout will
look broken while it happens. If you tell me the batch size before the day, I will raise the
ceiling for the window. This is a one-line env change on my side and a confusing afternoon
if we skip it.

**(d) Minidumps change the shape of a bundle, not the contract.** `cores_available` already
carries the Linux story. On Windows the equivalent question is whether the minidump was
written at all, and a `.dmp` compresses very differently from a `.zst` core — so the
hundreds-of-MB size path may simply never be exercised there. No change needed; I mention it
so that when Windows bundles all arrive at ~2 MB, neither of us reads that as a truncation
bug.

## 5. Fleet-scale numbers, so nobody has to rediscover them

My storage ceilings were sized for the pilot, and they are honest about where they stop:

| Ceiling | Value | Where it starts to bind |
|---|---|---|
| per-bundle | 512 MB | verified live at 500 MB, 138 MiB peak memory |
| per-station | 5 GB, oldest-evicted | never the newest bundle |
| whole store | **128 GB** | **~25 stations** at a full 5 GB each |
| self-registration | 20/hour | a batch install — see §4(c) |

So **around 25 stations is the point where the global cap becomes the real policy** rather
than the per-station one. That is not a cliff — the oldest bundles age out and manifests
(with backtraces) are kept forever regardless — but it is the number at which I should be
raising the store rather than discovering it from an eviction log. Tell me the target fleet
size when you know it and I will size for it in advance; there is 3.2 TB free on that
spindle, so the number is a policy choice, not a constraint.
