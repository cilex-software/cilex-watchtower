## §2 The events-rail 503s — your shed governor, most likely working as designed

`CvImageProvider.cpp:12` documents the contract: *"the event-snapshot path
503-sheds under memory pressure (the backend governor)"*, and the client already
gates itself to 2 concurrent with a 503 retry.

3,144 sheds against 1,543 genuine 404s says the dominant cause was **load, not
missing data** — which lines up with the week's memory thread: 12–13 GB swap,
`memory.swap.max = max` on all 17 containers, `s3` and `timescaledb` riding
their caps. It stopping on 2026-08-14 is consistent with your limit changes
landing.

**No ask here beyond confirmation** — if the sheds ended because of the −224 MB
retune, that is a nice independent corroboration of that work, and worth knowing.

## §3 THE ASK — the wall's snapshot 404s, 20,542 and current

This is the live one. `LiveThumb` draws the periodic still for a camera that has
no live decode slot — i.e. most of a dense wall. Those requests are 404ing in
volume and were still 404ing at **20:15 this evening**.

Please tell us:

1. **Is the snapshot endpoint `LiveThumb` calls still the right one?** If it
   moved or was renamed, 20,542 404s is simply a client on a stale path and we
   fix it in `qml/`.
2. **If it is right, why 404?** Two candidates we cannot separate from here: the
   camera has no recent snapshot stored, or the object is gone from storage
   (seaweed/s3 have been under pressure all week and `s3` sat at 98% of cap).
3. **Should a camera with no snapshot 404, or return a documented empty?** A 404
   is indistinguishable from a wrong URL at the client. If "no snapshot yet" is
   a normal state — and for a freshly provisioned camera it must be — it wants
   its own answer so we can render it honestly instead of guessing.

## §4 What is ours, and is being fixed regardless

Three client defects, all ours, none blocked on you:

1. **A failed thumbnail is indistinguishable from an absent one.** Both draw the
   same grey placeholder. An event with no clip and an event whose picture
   404'd must not look identical — that is our own no-invented-content rule and
   we are breaking it.
2. **No backoff.** 20,542 requests is a client retrying a known-failing URL
   indefinitely. On a box that has been shedding under memory pressure all week,
   our retry volume is plausibly *contributing* to the 503s in §2. That is
   embarrassing and it is the first thing we fix.
3. **We do not log the failing URL**, only the status — which is why this letter
   asks you what the endpoint should be instead of showing you what we called.
   Being fixed at the same time.
